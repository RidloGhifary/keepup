KeepUp Documentation

KeepUp is an ultra-lightweight, zero-dependency uptime monitor and public status page engine written in asynchronous Rust. It compiles all frontend assets, database migrations, and alerting routines into a single binary that idles with under 15MB of RAM.

Docker Quickstart

The fastest way to deploy KeepUp in production is using the official lightweight container image (~25MB total image size): 

docker run -d \
  --name keepup \
  -p 3000:3000 \
  -v ./data:/app/data \
  -e ADMIN_USER=admin \
  -e ADMIN_PASSWORD=supersecret \
  ridloghfry/keepup:latest

Once started, access the two endpoints:

  • Admin Dashboard: http://localhost:3000/ (Login with your configured credentials)
  • Public Status Page: http://localhost:3000/status (Customer-facing, no authentication required)

Docker Compose

For automated deployments with persistent storage and automatic restarts, create a docker-compose.yml:

version: '3.8'

services:
  keepup:
    image: ridloghfry/keepup:latest
    container_name: keepup
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - ./data:/app/data
    environment:
      - PORT=3000
      - KEEPUP_DB_PATH=/app/data/keepup.db
      - ADMIN_USER=admin
      - ADMIN_PASSWORD=change_this_to_strong_password
      - JWT_SECRET=generate_a_random_32_character_secret_here
      - RUST_LOG=keepup=info

Start the container in detached mode:

docker compose up -d

Building from Source & Cargo

KeepUp requires Rust 1.82+ to compile. Build the release binary or install directly into your Cargo environment:

# Clone the repository
git clone https://github.com/RidloGhifary/keepup.git
cd keepup

# Option A: Compile standalone release binary
cargo build --release
./target/release/keepup

# Option B: Install directly into your Cargo binary path ($HOME/.cargo/bin)
cargo install --path .
keepup

Environment Variables

Configure KeepUp via environment variables or a local .env file:

Variable Default Description
PORT 3000 HTTP port KeepUp listens on.
KEEPUP_DB_PATH data/keepup.db Filesystem path to the SQLite database file.
ADMIN_USER admin Username for dashboard authentication.
ADMIN_PASSWORD admin123 Password for dashboard authentication (strongly recommended to change in production).
JWT_SECRET keepup_jwt_fallback_secret_key_32bytes 32+ character HMAC secret for signing session cookies.
STATUS_PAGE_THEME auto Default status page aesthetic (auto, dark, oled, midnight, light).
CUSTOM_LOGO_URL None Optional image or SVG logo URL displayed in the status page header.
RUST_LOG keepup=info Log verbosity filter (trace, debug, info, warn, error).

SQLite & WAL Storage

KeepUp automatically initializes SQLite on startup with Write-Ahead Logging (PRAGMA journal_mode=WAL;) and PRAGMA synchronous=NORMAL;. This ensures high-throughput asynchronous writes from Tokio health check workers never block telemetry reads from the public status page or dashboard.

HTTP & HTTPS Probes

KeepUp supports flexible synthetic probes for web services and APIs:

  • Request Methods: GET, HEAD, POST with custom body payloads.
  • Custom HTTP Headers: Send custom User-Agent, Authorization tokens, or API keys.
  • Expected Status Code Ranges: Accepts ranges such as 200-299 or specific codes like 200,204,301.
  • Keyword Matching: Verifies that response body contains an expected string token (e.g. "status":"ok").

TCP Port Pings

Validate reachability and connection latency for databases, caching layers, and game servers (Postgres 5432, Redis 6379, SSH 22) using raw asynchronous TCP socket handshakes.

Failure & Retry Logic

To prevent false positive alerts caused by brief transient network blips, KeepUp tracks state transition counts. A service must fail consecutive checks equal to its configured max_retries (default: 3) before triggering a state change from UP to DOWN.

Scheduled Maintenance Windows

KeepUp allows operations teams to schedule upcoming downtime or maintenance windows in advance. When a window becomes active:

  • Announcement Banners: A prominent announcement banner is displayed at the top of all public status pages with title, description, and exact window timing.
  • Component Status Badges: Monitors linked to the maintenance window switch to an explicit MAINTENANCE state with distinct purple accent badges (#A855F7).
  • Incident Isolation: Expected downtime does not trigger incident alerts or degrade public reliability scores.

Alert Suppression Rules

During active maintenance windows, KeepUp automatically suppresses webhook alerts (Discord, Slack, Generic Webhook) for all covered monitors.

The background scheduler evaluates active windows dynamically during each check execution. If a target fails while its maintenance window is active (start_time ≤ now ≤ end_time), state transition notifications are paused. Once the maintenance window expires, regular alerting thresholds and recovery alerts resume seamlessly without manual operator intervention.

Maintenance REST API

Maintenance windows can be created, updated, and canceled via the administrative REST API: 

# Schedule a maintenance window
curl -X POST http://localhost:3000/api/admin/maintenance \
  -H "Content-Type: application/json" \
  -H "Cookie: keepup_session=<jwt_cookie>" \
  -d '{
    "title": "Database Engine Migration",
    "description": "Routine database maintenance and schema migrations.",
    "start_time": "2026-11-01T02:00:00Z",
    "end_time": "2026-11-01T04:00:00Z",
    "monitor_ids": ["mon_db_primary", "mon_api_gateway"]
  }'

Available maintenance endpoints:

  • GET /api/admin/maintenance — List all active, scheduled, and past maintenance windows.
  • POST /api/admin/maintenance — Schedule a new maintenance window.
  • PUT /api/admin/maintenance/:id — Update time bounds, description, or attached monitors.
  • DELETE /api/admin/maintenance/:id — Delete or cancel a scheduled maintenance window.

Generic Webhooks

For custom webhook integrations, Opsgenie, or incident response platforms, KeepUp dispatches structured JSON payloads for status transitions and recoveries:

  "event": "status_change",
  "monitor_id": "mon_01h8",
  "monitor_name": "Production API Gateway",
  "target_url": "https://api.example.com/health",
  "status": "DOWN",
  "response_time_ms": 142,
  "http_status": 502,
  "timestamp": "2026-10-31T12:00:00Z"

// Resolution Alert (UP)

  "status": "UP",

  "response_time_ms": 28,

Recovery Notifications

When a failing service recovers, KeepUp automatically calculates the exact downtime duration (e.g., "Downtime: 14 minutes, 20 seconds") and sends a resolution alert ([RESOLVED]) across configured channels.

Multi-Status Pages & Custom Slugs

KeepUp supports multi-tenant public status pages served on custom URL slugs (/status/:slug), allowing organizations to maintain isolated dashboards for different services, departments, or customer tiers (e.g. /status/api, /status/core, /status/internal).

The default status page at /status renders the default slug configuration, or falls back to showing all active monitors if unconfigured.

Monitor Grouping & Categorization

Monitors can be organized into distinct visual categories (such as “REST Endpoints”, “Databases”, or “Background Workers”) with explicit display ordering. 

# Create a custom status page with categorized monitor assignments
curl -X POST http://localhost:3000/api/admin/status-pages \
  -H "Content-Type: application/json" \
  -H "Cookie: keepup_session=<jwt_cookie>" \
  -d '{
    "slug": "api",
    "title": "API Systems Health",
    "description": "Real-time performance of public REST APIs and Webhook services",
    "is_public": true,
    "monitors": [
      { "monitor_id": "mon_01", "group_name": "REST Endpoints", "display_order": 0 },
      { "monitor_id": "mon_02", "group_name": "Webhooks", "display_order": 1 }
    ]
  }'

7-Day Uptime Timeline

The public status page renders a responsive 7-day interactive history bar for each public component. Each day represents the aggregated operational uptime percentage with tooltips showing exact percentages.

24-Hour Latency Chart

Monitors display a 24-slot hourly latency breakdown chart representing the past 24 hours chronologically. Bar heights scale proportionally to response latency, and bar colors reflect operational health.

Latency Percentiles (P50, P95, P99)

Beyond simple hourly averages, KeepUp computes precise response time percentiles directly from SQLite check history:

  • P50 (Median): 50% of requests experienced lower latency than this metric. Represents typical real-world response speeds.
  • P95 Tail Latency: 95% of checks responded faster than this threshold. Essential for identifying degradation under moderate traffic.
  • P99 Outlier Latency: 99% of requests completed faster than this time. Highlights extreme edge latency during GC pauses or network congestion.
  • 24-Hour Average: Weighted mean response time across all successful checks in the last 24 hours.

Percentiles are calculated in-memory over sorted check logs for high computational speed without heavy time-series dependencies: 

// Exposed in /api/public/status and /api/public/status/:slug
"latency": {
  "p50": 34,
  "p95": 89,
  "p99": 142,
  "avg": 41
}

Theme Customization

KeepUp status pages support 4 built-in aesthetic themes:

  • System Dark (default): Deep dark #0b0b0c canvas with glassmorphic cards.
  • OLED Pitch Black: Pure #000000 high-contrast styling for OLED displays.
  • Midnight Navy: Deep navy #050B14 background with subtle cyan glass borders.
  • Clean Light: Clean light gray #F5F5F7 styling with white translucent cards.

Visitors can toggle themes manually via the Sun/Moon button, or let the page match their OS mode via prefers-color-scheme.

Async Tokio Runtime

KeepUp's health check scheduler runs within Tokio's multi-threaded asynchronous runtime. Check workers run concurrently without blocking HTTP serving or database updates.

Security & Rate Limiting

KeepUp protects the admin dashboard against credential brute-forcing using tower-governor. Authentication utilizes constant-time string comparisons via the subtle crate, and issues 7-day signed HttpOnly, SameSite=Lax JWT session cookies.
